# GitHub Pages 公开试玩体验救援设计

日期：2026-07-16  
状态：已获用户批准，独立规格审查 APPROVED  
适用范围：浏览器公开试玩、GitHub Pages、本地 Playwright 验收

## 1. 问题与证据

真实 Pages 已成功部署并返回完整资源，但玩家体验仍不可接受：

- 1440×900 桌面中，960×540 固定画布只占中央区域，留下大量无意义留黑。
- 剧情、今日简报、目标、操作说明和提示同时显示，互相遮挡并裁切。
- 线上画面底部泄漏内部控制映射/函数文本，说明“调试状态正确”不能证明“玩家看到正确”。
- 736×414 小横屏只是压缩同一布局，文字重叠更严重。
- 390×844 竖屏把整个游戏压成约 390×219 的细条，没有触控入口或旋转引导。
- 现有 Pages 可玩性测试耗时约 2.2 分钟，并依赖调试快照、重复按键和测试钩子；它证明状态机可达，却不能证明新玩家能发现并完成流程。
- 现有截图证据主要验证非空像素、颜色数和画布不超出视口，没有验证文字边界、视觉层级、真实入口和移动端可操作性。

因此，本设计把“玩家可见证据”提升为独立质量维度，不再允许调试字段、像素非空率或测试钩子单独作为体验合格证明。

## 2. 目标与非目标

### 2.1 目标

1. 采用“世界优先”主界面：农庄地图是视觉主角，当前目标只保留一个明确动作和一个动机说明。
2. 吸收“四步纵切片”引导：让玩家持续知道 `开田 → 灵草 → 炼丹 → 引劫` 的关系，但引导可收起，不长期占据地图。
3. 桌面键鼠完整可玩；736×414 及更大的横屏提供触控；竖屏显示高质量旋转引导，不压缩完整游戏。
4. 剧情、任务、菜单和预览严格互斥，任何时刻只允许一个主注意力层。
5. 建立完整应用流程：标题/继续、序章、世界、炼丹、教学天劫、战后结算、暂停/设置和结局均有明确页面契约。
6. 让全部核心入口可发现：农务、出货、地点、背包、修行、炼丹、阵法、引劫；不可继续依赖隐藏的 F 键或标点快捷键。
7. 建立真实输入、视觉布局、触控、语义镜像和线上部署契约测试。
8. 保持 `src/sim` 确定、纯净且不依赖 DOM、PixiJS 或 LLM；若为五分钟纵切片增加教学天劫状态，也必须作为纯模拟规则实现并接受独立测试。

### 2.2 非目标

- 本轮不重写完整数值平衡、存档模型或内容体量；只允许为真实四段纵切片补充最小的教学天劫规则。
- 本轮不实现完整竖屏玩法；竖屏以清晰旋转引导和可访问说明为验收目标。
- 本轮不创建发布、部署 Pages、修改远端设置或更新 Golden Replay。
- LLM playtester 只作为无头策略与节奏补充，不替代真人可见 UI 验收。

## 3. 产品体验架构

### 3.0 应用流程状态机

新增单一 `AppFlowMachine`，替代“启动后直接挂载世界 + 多个局部布尔值”的隐式流程。

```text
boot
  → title
      → prologue → world
      → load → world
      → settings → title
world
  → alchemy → world
  → inventory/cultivation/map/pause → world
  → tribulation → aftermath → world
  → ending → title
```

每个状态必须定义进入条件、可用命令、可见层、退出目标、焦点目标和错误恢复。状态切换是唯一主覆盖层的权威来源；不再通过 `paused`、`dialogueBeat`、`locationSelectionActive`、`showInv` 等布尔值竞争决定顶层页面。

| 页面                      | 必须可见                            | 主 CTA             | 退出/恢复                 |
| ------------------------- | ----------------------------------- | ------------------ | ------------------------- |
| Title                     | Logo、版本、新游戏、继续、设置      | 新游戏或继续       | 设置返回标题              |
| Prologue                  | 短叙事、继续、跳过、当前教学动作    | 继续/跳过          | 进入 World，旗标一致      |
| World                     | 世界、状态带、一个当前目标、操作带  | 当前上下文动作     | 打开一个 Overlay          |
| Alchemy                   | 材料、丹方、火候、结果预览、出丹    | 炼制首枚备劫丹     | 成功后回 World 并推进旅程 |
| Tribulation               | 雷预警、剩余雷数、HP、丹药/阵法动作 | 承受或规避本轮雷击 | 结束后必进 Aftermath      |
| Aftermath                 | 损失、收益、淬体/突破、下一目标     | 返回农庄           | 回 World，状态已保存      |
| Inventory/Cultivation/Map | 当前内容、选择、返回                | 具体操作或查看     | 返回按钮恢复 World        |
| Pause/Settings            | 继续、控制、音量、可访问性          | 保存设置或继续     | 恢复原状态与焦点          |
| Ending                    | 结局、统计、重玩/标题               | 返回标题           | 明确处理存档              |

标题、炼丹、天劫、战后结算和设置不得只以 Toast 或调试状态存在；它们必须是可截图、可聚焦、可返回的真实界面。

### 3.1 世界优先主界面

内部逻辑画布继续使用 16:9 坐标系，CSS 将其等比放大到视口允许的最大尺寸。桌面不再设置 960px 的 CSS 最大宽度；画布在 1440×900 下应接近 1440×810，在 736×414 下填满横屏。

主界面分为四个稳定区域：

1. **顶部状态带**：日期、境界、寿元、炉温和三条核心资源，仅一行显示。
2. **世界区域**：占可用宽度约 72%–78%，承载地图、玩家、作物、设施和环境反馈。
3. **当前目标轨**：占约 22%–28%，只显示当前目标、即时操作和“为什么值得做”。不得显示完整帮助词典。
4. **上下文操作带**：底部显示当前工具、可执行动作和 4–6 个主要入口；操作随状态变化，不堆叠整套键位表。

任务轨初始包含一个可收起、但必须真实完成的四段纵切片：

1. **获得第一批灵草**：在世界中完成翻地、播种、浇水和首批可用灵草获取。每个动作有空间入口、输入提示、即时反馈、完成反馈和下一步 CTA。
2. **炼出首枚备劫丹**：通过可见丹炉入口进入 `Alchemy`，选择现有材料、控制火候并完成一次真实炼制；失败必须能重试且不能造成新档软锁。
3. **完成教学小天劫**：丹药完成后解锁一次确定性的低风险教学天劫。它使用正式的雷预警、HP、丹药和阵法/走位命令，但有独立参数和一次性旗标，不伪装成正式境界突破。
4. **查看战后结算**：天劫结束必进入 `Aftermath`，展示损失、收益、淬体进度和下一目标，再返回农庄。

这四段是公开试玩的 3–5 分钟纵切片。现有“出货、补种、第二轮浇水”十步农务循环保留为后续日常引导，但不再冒充完整公开纵切片。完成教学天劫后，旅程折叠为紧凑进度，不持续遮挡世界。

教学天劫必须满足：

- 使用确定种子和正式 `PlayerAction`/事件输出，不在渲染层伪造结果。
- 不直接提升正式境界；只授予明确、有限的淬体进度或教程奖励。
- 可失败但默认不永久死亡；失败进入 Aftermath，说明原因并允许重新准备。
- 教学完成旗标进入存档，重复加载不会重复发奖。

### 3.2 注意力层互斥

渲染层建立显式 UI 模式：

- `world`：世界 + 状态 + 当前任务 + 操作带。
- `dialogue`：世界降噪 + 单一短对话；任务轨和其它预览隐藏。
- `panel`：一个交互面板 + 对应项目预览；今日任务和地点预览隐藏。
- `location`：地点目录 + 当前地点说明；其它面板隐藏。
- `pause`：暂停菜单；除背景世界外全部交互冻结。
- `ending`：结局层；最高优先级。
- `portrait-gate`：DOM 竖屏旋转提示；Canvas 游戏交互暂停。

模式由单一派生函数决定，禁止各组件自行竞争 `visible`。同一帧最多存在一个主覆盖层。

### 3.3 剧情与首次可操作时间

- 初始剧情改为短节拍，每页最多 2–3 行，并明确显示“继续/跳过”。
- 玩家可随时跳过序章；跳过不破坏叙事旗标和存档一致性。
- 序章结束后首先出现一个动作：面对空地翻地。不得同时要求玩家阅读完整经济、炼丹和引劫说明。
- 每次动作成功使用地图反馈、短 Toast 和任务进度三者中的至多两种，避免重复播报。
- 失败反馈必须说明原因和下一步，而不是静默无效。

### 3.4 核心入口

上下文操作带和菜单必须提供可见入口，而不是只在键盘映射中存在：

- 主动作：翻地/播种/浇水/收获/确认。
- 农庄：农务、出货、加工、设施。
- 地点：地点目录与服务。
- 修行：体魄、丹药、阵法、引劫准备。
- 背包：物品与关键资源。
- 系统：暂停、音量、控制说明、存档状态。

键盘快捷键保留为加速路径；可见菜单是权威入口。所有入口通过统一命令层调用同一业务函数，禁止 DOM 触控复制玩法逻辑。

## 4. 响应式与输入设计

### 4.1 桌面

- 视口大于等于 900×506 时使用完整世界优先布局。
- Canvas 等比填充可用视口，保留 16:9；允许少量背景留边，但不得固定停在 960px。
- 文字按逻辑画布尺寸布局，不依赖 CSS 缩放后的偶然可读性。

### 4.2 横屏触控

- 视口横向且短边不小于 360px 时启用 DOM 触控层。
- 左下为方向控制；右下为主动作和次动作；底部中间显示当前任务。
- 触控按钮至少 44×44 CSS px，互相留有间距，并具备可读标签、按下态和禁用态。
- 触控层只分发统一命令，不直接修改模拟状态。
- 浏览器滚动、双击缩放和长按菜单不得抢占游戏操作。

### 4.3 竖屏

- 竖屏不渲染缩成细条的完整 HUD。
- 显示品牌化旋转提示、当前存档安全说明和“旋转设备继续”。
- 提示是 DOM 内容，屏幕阅读器可读；切换横屏后自动恢复游戏并重新聚焦。

### 4.4 键盘与可访问语义

- Canvas 获得清晰焦点样式和说明。
- DOM 语义镜像暴露：当前日期、核心资源、当前目标、可用动作、打开的面板和结果反馈。
- 动态结果通过节制的 `aria-live` 区域播报；连续帧更新不得刷屏。
- 主要菜单与触控按钮使用真实 `button`，支持 Tab、Enter 和 Space。
- Canvas 内关键交互区域与语义按钮保持一一对应，符合 HTML Canvas fallback/可访问性原则。

## 5. 技术边界

### 5.1 模块

建议新增或拆分：

- `src/app/appFlowMachine.ts`：Title、Prologue、World、Alchemy、Tribulation、Aftermath、Ending 的顶层状态机。
- `src/app/onboardingDirector.ts`：四段纵切片，只消费模拟事件和公开状态，不硬编码具体按键。
- `src/app/uiMode.ts`：从应用状态派生唯一 UI 模式与可见层。
- `src/app/semanticInputRouter.ts`：统一 `move/interact/cancel/tool/action/menu`，下接键盘、鼠标和触控适配器。
- `src/app/journeyGuide.ts`：四步纵切片进度与当前行动文案。
- `src/app/responsiveShell.ts`：视口模式、竖屏门、DOM 触控和语义镜像。
- `src/render/viewportLayout.ts`：逻辑坐标、safe-area、区域边界、文字容量和触控坐标映射。
- `src/render/worldScene.ts`：只绘制世界、角色、作物、设施和空间入口。
- `src/render/hudLayer.ts`：状态、当前目标和上下文动作。
- `src/render/overlayStack.ts`：炼丹、背包、修行、地图、暂停、战后结算的互斥与焦点。
- `src/render/renderer.ts`：只消费布局与派生视图模型，不再散布固定坐标和竞争可见性。
- `tests/browser/scenarioFactory.ts`：只建立确定性页面 fixture；不替真实新档纵切片完成动作。

`src/app/main.ts` 负责组合，不继续吸收新的布局、输入和引导分支。

### 5.2 渲染性能

- HUD、任务和帮助文本只有值变化时才更新 `.text`；不得在 ticker 每帧无条件重栅格化 Pixi `Text`。
- 高频数字可迁移到 `BitmapText`；中文长文本继续使用 `Text`，但更新受缓存保护。
- 截图测试使用统一 Chromium、字体、SwiftShader 和分辨率环境。
- 生产默认不启用 `preserveDrawingBuffer`；测试截图使用 `locator('canvas').screenshot()` 或显式测试构建。

### 5.3 错误与降级

- 初始化期间显示 DOM 加载状态，不得只显示空黑框。
- WebGL/Pixi 初始化失败时显示可读错误、刷新建议和兼容性说明。
- 资源缺失时允许程序化占位，但在控制台和调试契约中记录；关键 UI 文本不得消失。
- 本地存档解析失败应回退新档并给出一次非阻塞提示。

## 6. 自动化测试设计

### 6.1 单元与属性测试

- `uiMode`：所有覆盖层组合都产生唯一模式；结局、暂停和竖屏优先级确定。
- `layout`：桌面、横屏和竖屏的区域不重叠，文字盒不越界，触控区满足最小尺寸。
- `journeyGuide`：每个 onboarding 状态映射到一个当前动作、一个动机和四步进度。
- `gameCommands`：键盘、鼠标和触控映射到同一命令；命令不直接依赖 DOM。
- 保持现有 sim 属性、Golden Replay 和集成测试不变，除非真实玩法行为被明确接受为变更。

### 6.2 浏览器玩家路径

新增两类严格分离的玩家路径。

**新档四段纵切片**：

1. 打开游戏并跳过或完成短序章。
2. 只使用玩家可见控件获得第一批灵草。
3. 通过可见入口完成一次炼丹。
4. 通过可见入口开始并完成教学小天劫。
5. 阅读 Aftermath 并返回农庄。

全程不得调用 `__AEON_TEST__`。横屏触控路径全程不得用 `page.keyboard` 代替触控。

**独立页面 fixture**：

- 可用确定性 ScenarioFactory 直接打开 Title、Alchemy、Tribulation、Aftermath、Inventory、Pause 等页面做布局和异常状态测试。
- fixture 只证明单页契约；不得被描述为新玩家完成了纵切片。

调试快照只用于观察结果。测试钩子可用于长周期平衡/成长回归，但不能作为公开试玩可玩性的证据。

### 6.3 视觉与布局

- 固定环境下使用 Playwright `toHaveScreenshot()` 保存评审过的 Title、World、Alchemy、Tribulation、Aftermath、Inventory 和 Pause 基准。
- 覆盖桌面 1440×900、960×540，横屏触控 844×390、736×414，以及竖屏 390×844。
- 断言 Canvas CSS 尺寸既不越界，也达到预期最小占屏比例。
- 断言 Pixi 文本和面板的渲染边界位于各自布局区域内；正文有效字号至少 12 CSS px，关键动作至少 14 CSS px。
- 断言触控目标至少 44×44 CSS px，位于 safe-area 内且互不遮挡。
- 断言玩家可见文本不包含 `function`、`=>`、内部命令标识或未翻译键。
- 竖屏截图必须是旋转门，而不是压缩游戏。
- 非空像素率和颜色数保留为最低 smoke，不能替代视觉基准。

### 6.4 触控与可访问性

- Playwright 使用真实 pointer/touch 点击方向、主动作和菜单按钮。
- 验证按钮尺寸、可见标签、焦点顺序、键盘激活和 `aria-live` 结果。
- Canvas 本体之外存在可读取的当前目标和主要入口。
- 使用 axe 或等价规则检查 DOM 外壳；Canvas 玩法语义通过项目自定义断言补足。

### 6.5 线上部署契约

- 本地公开树和真实 Pages 暴露版本化的只读调试契约，例如 `debugSchemaVersion` 和 `buildRevision`。
- 线上截图/可玩测试先核对契约版本，避免本地测试对旧 bundle 读取不存在字段。
- Pages 验收包含真实页面截图、远端四段纵切片和关键入口可见性；仅 HTTP 200、Canvas 存在或调试状态可达不算通过。

## 7. 验收标准

1. 1440×900 下游戏画面占据主要视口，不再固定为 960×540；无文字或面板越界。
2. 736×414 与 844×390 横屏可通过触控完成四段纵切片；全程不使用键盘替代触控。
3. 390×844 竖屏显示旋转提示，游戏不会缩成不可读细条。
4. 序章、任务、地点、交互面板和暂停层满足单一主覆盖层不变量。
5. Title、World、Alchemy、Tribulation、Aftermath、Inventory、Pause/Settings 均为可见、可聚焦、可返回、可截图的真实页面。
6. 新玩家不依赖 README、设计文档、F 键或标点快捷键即可获得灵草、炼丹、完成教学天劫并查看结算。
7. 新档纵切片测试不使用测试钩子；测试钩子仅用于独立页面 fixture 或较长时间跨度回归。
8. 视觉基准覆盖五个视口和七类页面，并能捕获文字泄漏、裁切、叠压、过小字号、过小触控目标和竖屏缩放。
9. DOM 语义镜像可读取当前目标和可用动作，主要控件可用键盘和触控激活。
10. 修复浏览器测试中的未调用断言/动作，并增加静态检查，防止 `expect(...).toBeVisible;`、`locator.click;` 等伪测试再次出现。
11. 真实 Pages 部署验收运行同一条远端四段纵切片，而不只是 Canvas smoke。
12. `pnpm governance:check`、`pnpm typecheck`、`pnpm test`、`pnpm build` 通过；相关 Playwright 套件通过。
13. 保持 `src/sim` 的确定性和无 IO/渲染依赖，不提交 Agent 状态、生成物、存档、密钥或生产 sourcemap。

## 8. 实施顺序

1. 建立 `AppFlowMachine`、`OnboardingDirector`、`ViewportLayout`、统一语义命令和响应式 DOM 外壳，并用单元测试锁定边界。
2. 实现 Title/Prologue/World 基础流程，重排 Pixi 世界、HUD 与互斥覆盖层，移除固定 CSS 宽度和每帧无条件文字更新。
3. 实现真实 Alchemy 页面和首枚备劫丹任务。
4. 实现确定性教学天劫与 Aftermath 页面；若触及 sim 行为，先补模拟测试，再评估 Golden Replay 是否属于已接受行为变更。
5. 接入横屏触控、竖屏门、语义镜像、可见主菜单和设置入口。
6. 新增真实纵切片、页面视觉、触控、可访问性、伪断言静态检查和 Pages 契约测试。
7. 黑盒试玩桌面、横屏和竖屏，修复后再运行完整治理门禁。

## 9. 技能选择

- 使用仓库内官方 PixiJS `application`、`text`、`accessibility` 和 `performance` 技能指导实现。
- 使用 `frontend-design` 保障世界优先界面的产品化视觉层级。
- 使用 `baseline-ui`、`fixing-accessibility` 和 `web-design-guidelines` 审核 DOM 外壳与触控。
- 使用 `visual-review` 和 `dogfood` 做真实截图与玩家路径验证。
- 使用项目 `llm-playtester` 评估后续策略/节奏，但不让 LLM 进入 `src/sim`，也不让它替代 UI 验收。
