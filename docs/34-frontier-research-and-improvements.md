> 方法：arXiv（ Sokoban PCG 精确检索）+ PCG 书 + npm/GitHub 生态扫描 +

## 一、Sokoban 生成前沿：扩散模型 vs 构造式

### 最新论文（arXiv:2608.15958, 2026-08）

Baghal 提出用 transformer 掩码扩散模型生成 Sokoban 关卡（训练于
DeepMind Boxoban 数据集），**77.4% 可解率**；剩余失败中 94.5% 仅需
移除一堵墙即可解。

**与本项目对比**：

| 维度 | 扩散模型（论文） | 本项目构造式 |
|------|----------------|-------------|
| 可解率 | 77.4%（需后验修复） | **100%**（构造保证） |
| 难度控制 | 不可控（模型黑盒） | **精确**（认证步数=难度度量） |
| 运行时间 | 推理 ~秒级 | **构造 <5ms**（stage 0） |
| 确定性 | 采样随机 | **注入 Rng 完全可复现** |

**结论**：本项目构造式路线在所有关键维度优于扩散模型。扩散模型适用
场景是缺乏构造约束的复杂关卡（10×10 多箱），本项目 6×6 单箱不需要。

## 二、Sokoban 求解谱系与死锁分类

（经 Wikipedia 核实）

- **NP-hard**（Fryers & Greene 1995）→ **PSPACE-complete**（Culberson 1997;
  Hearn 2006）：可解性判定不存在多项式时间算法，有界 BFS 是合理选择。
- **Rolling Stone**（U Alberta）：首个自动求解器，**死锁检测为核心增强**。
- **Festival**：FESS 算法，首个全解 XSokoban 标准测试集。
- 死锁类型：方块卡死角/卡墙/堵路。本项目哨兵用有界重解检测，比分类学
  检测更精确但有节点上限（已对齐认证界 40000，§22 零误报验证）。

## 三、游戏手感（Game Feel）可落地改进

基于 2D 益智游戏通用最佳实践，本项目可落地的改进按影响排序：

### 3.1 输入缓冲（Input Buffering）

**现状**：每次按键同步消费，快速连按可能丢失。
**改进**：缓存最近一次按键 ~150ms，在移动冷却结束后消费缓存。
**预期效果**：手感提升显著——玩家感觉"按键总是有响应"。
**成本**：低（~20 行，session 层输入队列）。

### 3.2 推石反馈强化

**现状**：推石成功后光路立即重绘，但推石本身无视觉/音效反馈。
**改进**：推石瞬间添加 micro-screen-shake（1-2px）+ 推石粒子
（金石碎片从镜底弹出）。
**预期效果**：每次推石都有物理反馈感。
**成本**：低（复用已有 triggerShake + spawnBurst 基础设施）。

### 3.3 首步高亮增强

**现状**：首步提示（H）给方向文字，但不在棋盘上可视化。
**改进**：在首步方向的目标阵石格上添加高亮边框脉冲。
**预期效果**：新手第一次玩就能理解推石方向。
**成本**：中（需在 draw() 中根据 hintDirection 渲染高亮框）。

### 3.4 光路预览增强

**现状**：ghost 预览（docs/31 §2.3）显示推后光路，但仅从镜方推入方向。
**改进**：光路颜色编码——如果推后光路命中甜蜜区则金色，命门但非甜蜜
则蓝色，不命中则灰色。让玩家推前就能预判结果质量。
**预期效果**：高级玩家可以精确规划；新手也有直觉反馈。
**成本**：中（需在 ghostBeam 计算中加入 evaluateTribulation 功率判定）。

### 3.5 音效分层

**现状**：音效仅在结算时触发（brew/explosion/breakthrough）。
**改进**：推石时 tick 音效、光路转向时 whoosh、命门命中时 chime、
herb 烧毁时 crackle。
**预期效果**：听觉反馈强化因果链感知。
**成本**：中（需生成或录制音效素材）。

## 四、roguelite 设计范式

### 4.1 跨世 meta-progression

**现状**：换代传承选知识 + 遗物（二元选择），效果限于下一世起手。
**范式参考**：成功 roguelite（Hades、Dead Cells、Slay the Spire）的
meta-progression 通用模式——每次死亡后获得**永久货币**解锁**技能树**。
**本项目适配**：劫灰碑记的悟痕（insight budget）可以跨世累积为
残卷科技树节点，而非一次性选择。但这改变了核心循环，需维护者决策。

### 4.2 难度曲线自适应

**现状**：难度带按 stage 线性/查表，不因玩家表现调整。
**范式参考**：DDA（Dynamic Difficulty Adjustment）基于玩家表现指标
动态调整参数（如自动降低 minTemperingPower 若连续失败）。
**本项目适配**：cultivation-metrics 的 per-policy 数据已提供基线，
可在此基础上实现"连续 N 次 insufficient 后自动降 min 斜率 ±1"。
**成本**：高（需改 sim + 重授权夹具），建议真人试玩数据支撑后再做。

### 4.3 种子选择与每日挑战

**范式参考**：Slay the Spire 的每日挑战（固定种子 + 修改器）。
**本项目适配**：天劫棋盘 seedSalt 可由日期哈希生成，同一天所有玩家
面对同一劫盘——增加社区讨论性。
**成本**：低（仅改 seedSalt 来源），但需先做完真人试玩确认基础体验。

## 七、补充调研：叙事脚本语言 / meta-progression / Sokoban 基准（2026-09-15）

### 7.1 Ink 叙事脚本语言（inkle）→ narrationScenes 对标

Ink（inkle 工作室，MIT 开源）是交互式叙事的行业标准，被 80 Days、
Sorcery!、Disco Elysium 等使用，累计数百万字内容。核心特性：

| Ink 特性 | 本项目 narrationScenes | 差距 |
| -------- | ---------------------- | ---- |
| Knots/Stitches（命名叙事节点） | NarrationScene（id + act） | 等价 |
| Choices（条件分支选项） | NarrationChoice（→ Effect） | Ink 支持条件显示 + 变量赋值；本项目 Effect 标签够用 |
| Variables（叙事状态跟踪） | 直接读写 CultivationRunState | **Ink 强项：跨场景变量可跟踪关系/好感度**；本项目用 runState 字段替代 |
| Tunnels（可复用序列） | 无 | Tea Shed / Greenhouse 等重复场景可用 tunnel 模式去重 |
| Threads（并行故事线） | 无 | 当前叙事为线性链，无需并行 |
| Diverts（跳转到任意节点） | choices → Effect → 固定下一步 | Ink 支持 divert 到任意 knot；本项目只有线性 + 汇流 |

**结论**：当前 58 scene 规模下 narrationScenes 足够。若内容扩至 100+
scene 或需要跨场景变量跟踪（如 NPC 好感度），建议迁移到 Ink 或
自建变量跟踪层。短期不建议——迁移成本高且现有内容未触及瓶颈。

### 7.2 Hades 设计范式 → cultivation-run 对标

经 Wikipedia 详细抓取，Hades 的 roguelite 循环有以下可借鉴模式：

| Hades 模式 | 本项目现状 | 差距与建议 |
| ---------- | ---------- | ---------- |
| **死亡即推进**（每次死亡推进关系/故事） | ✅ 劫灰传承 → heir 叙事 | 已实现等价 |
| **混合 meta-progression**（死亡消失 + 永久两类货币） | ⚠️ 悟痕 = 永久，灵草/丹药 = 消失 | 已实现等价，但缺少「消失货币的跨世转化」——Hades 末神赐 → 本项目可有「劫后余晖」跨世残卷解锁 |
| **叙事穿插 run 间**（hub 对话推进） | ✅ 叙录系统 | 已实现 |
| **武器多样性**（多武器定义不同攻击模式） | ⚠️ 修途活动 = 「武器」 | 已通过六格日程实现差异化 |
| **Pact of Punishment**（自选难度↑ 换奖励↑） | ❌ 无 | **建议**：天劫前可选「加强劫」（更多阵石/更短余步）换更高悟痕产出——低成本高回报 |
| **God Mode**（每次死亡+耐久） | ✅ 引导触达 + 先锻体提示 | 已实现等价（可访问性杠杆） |

**最有价值的借鉴**：**Pact of Punishment 模式**——玩家自选难度换收益。
实现方式：劫抉屏增加「加强劫」选项（勾选后 stageMinTemperingPower +
4、余量 −4，悟痕产出 ×2），用已有 `cultivation:metrics` 工具校准。
低成本（UI + 参数覆盖，不碰 sim 核心逻辑），且与 §18 窗口边界数据
兼容（6,125 的平台在 min 10 时仍有余量）。
